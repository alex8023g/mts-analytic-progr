# prerequire

- Python 3.13+
- Node.js 24+
- PostgreSQL 15+

# .env

- backend: обязателен (DATABASE_URL) — создаётся на основании backend/.env.example
- frontend: необязателен; две переменные:
  - `API_URL` — адрес backend для серверных запросов (server actions + route handler `/api/export`), по умолчанию `http://127.0.0.1:8000`. Браузер по нему не ходит, поэтому он может оставаться приватным
  - `NEXT_PUBLIC_WS_URL` — адрес backend WebSocket для прогресса импорта/экспорта, по умолчанию `ws://127.0.0.1:8000`. Браузер подключается к нему напрямую, поэтому в проде он должен быть доступен из браузера (например `wss://api.example.com`)

# запуск

1. убедиться, что PostgreSQL запущен
2. в папке backend создать .env файл на основании .env.example и указать в нём DATABASE_URL
3. (опционально) frontend обращается к backend только со стороны сервера по адресу `API_URL` (по умолчанию `http://127.0.0.1:8000`); если backend на другом адресе — указать его в frontend/.env: `API_URL=http://...`
   далее все команды выполняются из корневой папки
4. установить зависимости: `npm run install:all`
5. создать базу данных и таблицы: `npm run db:create`
6. запустить backend: `npm run backend:prod`
7. собрать fronted: `npm run frontend:build`
8. запустить frontend: `npm run frontend:prod`

# обработка повторяющихся и неоднозначных записей

4е Семенова это один человек или 3 или 4 разных человека?
то ли при увольнении добавляется новая запись, то ли при переходе на другую должность добавляется новая запись, то ли при повторном приеме обновляется существующая запись?

явно не хватает даты рождения сотрудника для определения его уникальности

видна закономерность: некоторые уволенные сотрудники имеют запись со статусом Работает в том же отделе с той же датой приема на работу

принимаем утверждение, что записи с одинаковыми фио и одинаковым отделом и одинаковой датой приема на работу - это запись одного и того же человека и оставляем только запись в которой есть дата увольнения

также есть записи с приемом на работу в ту же дату с тем же фио, но в другом отделе;

т.к. нет достаточно данных (нет даты рождения сотрудника) и негде уточнить логику (возможно сотрудника перевели в другой отдел, но т.к. нет даты перевода, то невозможно определить какой из отделов актуальный а какой нет) также маловероятно что это полные тезки, которых приняли на работу в один и тот же день в разные отделы, поэтому принимаем что это запись одного и того же человека и оставляем только запись в которой есть дата увольнения

актуальность данных на выбранную дату определяется следующим образом: если дата приема сотрудника больше то этот сотрудник еще не принят на работу и он не отображается, если дата увольнения больше выбранной даты а дата приема на работу меньше, то сотрудник отображается со статусом Работает, если дата приема на работу и дата увольнения меньше выбранной даты, то сотрудник отображается со статусов Уволен.

# WebSocket (статусы импорта и экспорта)

прогресс длительных операций (импорт файла, формирование экспорта) транслируется клиенту через WebSocket в реальном времени

endpoints (backend):

- `/ws/imports/{job_id}` — статус и прогресс импорта
- `/ws/exports/{job_id}` — статус и прогресс экспорта

события (JSON, сервер → клиент):

- `{"type": "status", "stage": "started"}` — операция началась
- `{"type": "progress", "processed": N, "total": M}` — обработано N из M строк (повторяется)
- `{"type": "result", ...}` — операция успешно завершена (для импорта содержит итоги, для экспорта — имя файла)
- `{"type": "error", "detail": "..."}` — ошибка

поток:

1. клиент генерирует `job_id` (`crypto.randomUUID()`) и сначала открывает WebSocket
2. затем запускает саму операцию с тем же `job_id`: импорт — `POST /imports?job_id=...`, экспорт — `GET /export?...&job_id=...`
3. сервер выполняет тяжёлую работу в отдельном потоке (`asyncio.to_thread`), чтобы event loop оставался свободным, и публикует события по ходу выполнения
4. WebSocket закрывается после терминального события (`result` или `error`)

реализация:

- backend: in-memory pub/sub (`app/services/progress.py`, `ProgressHub`) — на каждый `job_id` одна очередь; общий обработчик WebSocket `stream_job_events` переиспользуется обоими endpoint'ами. Состояние хранится в памяти процесса, поэтому предполагается один воркер (WebSocket и сам запрос должны попасть в один процесс)
- сам результат операции по-прежнему приходит и по HTTP (ответ на `POST /imports` / тело файла на `GET /export`), поэтому WebSocket — необязательное улучшение: если он не подключился, операция всё равно выполнится, просто без индикатора прогресса
- frontend: браузер подключается к backend напрямую по `NEXT_PUBLIC_WS_URL`; при импорте показывается прогресс-бар, при экспорте — модальное окно с прогрессом
